## The sweep program

Tasks 1 and 2 both use this ordered `sed` program. **The order is load-bearing
and was verified empirically, not assumed.** `\bpluton\b` does not match the old
name when a word character follows it, because there is then no boundary after
the `n`. That blind spot is wide, and Task 1 walked into the part of it this plan
had not anticipated:

| Shape | Real instances | Why the generic rule misses it |
|---|---|---|
| `pluton_<word>` | `pluton_file` 21 times, `pluton_core`, `pluton_tests`, `pluton_test`, and four test function names ending `_pluton_error` or similar | the underscore is a word character |
| `Pluton<Word>` | `PlutonFormatError` 120, `PlutonIOError` 20, `PlutonVersionError` 12 | the capital is a word character |
| `PLUTON_<WORD>` | `PLUTON_TEST_DATA` in `cpp/tests/` | as above, and the case differs |

The single rule `s/pluton_/bermake_/g` covers the whole first row, which is why it
replaces the narrower `pluton_core` rule this plan originally carried. Without it
Task 2 renames the module file to `bermake_file.py` while leaving 21 imports
pointing at `pluton_file`, and every one of them raises ImportError. The uppercase
row was cleared by Task 1 and none remains outside `docs/`, verified by search, so
no uppercase rule is needed.

The extension rule must also precede the generic one, or `.pluton` becomes
`.bermake` instead of `.berm`.

**Write it with a quoted heredoc, never with `printf`.** This was found the hard
way while validating this plan: `printf` reads `\b` as an escape and writes byte
0x08, a literal backspace, into the script. Five of the eight rules then stop
matching, the tree ends up half-renamed, and nothing reports an error. Write it
once, to the scratchpad, as `sweep.sed`:

```bash
cat > "$SWEEP" <<'SEDEOF'
s/pluton_/bermake_/g
s/PlutonFormatError/BermakeFormatError/g
s/PlutonIOError/BermakeIOError/g
s/PlutonVersionError/BermakeVersionError/g
s/pluton3d\.org/bermake.org/g
s/\.pluton\b/.berm/g
s/\bpluton\b/bermake/g
s/\bPluton\b/Bermake/g
SEDEOF
```

Then run both checks below. Neither is optional, and the first is the one that
catches the corruption described above, which is invisible in ordinary output.

Check one, that no control character reached the file:

```bash
grep -c $'\x08' "$SWEEP"
```

It must print `0`. Anything else means the script is corrupt: rewrite it with the
heredoc above rather than trying to repair it.

Check two, that the rules do what they claim. Note that this dry run is itself a
`printf`, which is safe because `\n` is the escape it is meant to interpret:

```bash
printf 'pluton_core\nfrom pluton.io.pluton_file import SCHEMA_VERSION\ntest_os_error_is_not_a_pluton_io_error\nPlutonFormatError\nPlutonIOError\npluton::mesh\n#include "pluton/mesh.h"\nx.pluton\npython/pluton/app.py\nhttps://pluton3d.org\nPluton files (*.pluton)\npluton = "pluton.app:main"\n' | sed -f "$SWEEP"
```

Expected output, exactly:

```
bermake_core
from bermake.io.bermake_file import SCHEMA_VERSION
test_os_error_is_not_a_bermake_io_error
BermakeFormatError
BermakeIOError
bermake::mesh
#include "bermake/mesh.h"
x.berm
python/bermake/app.py
https://bermake.org
Bermake files (*.berm)
bermake = "bermake.app:main"
```

If any line differs, stop and report. A wrong sweep program silently half-renames
500 files. The `Pluton files (*.pluton)` line is the one that proves the two file
dialog filters are carried by the sweep rather than needing hand edits.

An earlier draft of this step compared `bermake.__version__` to `_core.version()`.

today. They are pre-existing and out of scope here; see the ledger.

lives in a different file from the C++ literal and neither is derived from the
other. **Nothing in the suite compares those two**, so a bump applied to one and
not the other is invisible. Verified: the metadata and the compiled string are
read from independent sources.

```python
def test_the_declared_and_the_compiled_version_agree():
    """Catches a version bump applied to one file and not the other.

    Not a comparison of `__version__` against `_core.version()`: those are the
    same call, since `__init__` assigns `__version__ = version()` with `version`
    imported from `_core`, so such a test cannot fail. The hand-edited version in
    pyproject.toml reaches the installed distribution metadata, and the C++
    literal reaches `_core.version()`, and nothing derives either from the other.
    Pinning the expected value as well catches a bump that was never applied at
    all, and catches an editable install that was not refreshed after the bump.
    """
    from importlib.metadata import version as distribution_version

    from bermake import _core

    assert distribution_version("bermake") == _core.version() == "0.14.0"
```

### Task 5: The guard test

**Files:**
- Test: `tests/test_no_stale_product_name.py` (create)

**Interfaces:**
- Consumes: the finished state of Tasks 1 through 4.

This is the test that catches the reference nobody thought of. It has one
failure mode of its own, and this project has hit it three times: a guard that
searches an empty or wrong scope passes while proving nothing. **The test must
assert its own scope matched a plausible number of files.**

- [ ] **Step 1: Write it**

```python
"""A guard against the retired product name surviving in shipped code.

Scoped deliberately. docs/ retains thousands of occurrences on purpose (spec
D6), and tests/data/ keeps the old name as fixture provenance (spec D11), so a
repository-wide search would fail by design. This looks only at what ships.

The scope assertion is not decoration. A guard test that walks an empty tree
passes while proving nothing, which is the exact failure this project produced
three times during M7.7, twice in test code and once in a verification script.

__pycache__ is excluded deliberately rather than left to the UnicodeDecodeError
branch below. There are around 150 stale .pyc files under the package, every one
of which contains the old module path, and all 150 do currently raise on a strict
utf-8 decode, so the guard would pass either way today. Depending on that is
wrong twice over: bytecode is not shipped source, and a single .pyc that happened
to decode would turn this guard into a false positive nobody could explain. The
real scope with the exclusion is around 220 files, comfortably above the
threshold.
"""

from pathlib import Path

import pytest

ROOT = Path(__file__).resolve().parent.parent
SHIPPED = (ROOT / "python" / "bermake", ROOT / "cpp")


def _text_files():
    for tree in SHIPPED:
        for path in tree.rglob("*"):
            if not path.is_file():
                continue
            if "__pycache__" in path.parts:
                continue
            if path.suffix in {".glb", ".png", ".jpg", ".ico"}:
                continue
            yield path


def test_the_guard_actually_has_a_tree_to_search():
    """Without this, every assertion below is vacuous."""
    files = list(_text_files())
    assert len(files) > 150, f"guard scope collapsed to {len(files)} files"
```
