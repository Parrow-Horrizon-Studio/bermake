# M7.12: Autosave and crash recovery

**Status:** draft for review, 2026-10-04.
**Issue:** #77 (autosave to a sidecar with crash recovery on next launch, plus File > Revert to Saved).
**Milestone order:** M7.11 (the quick pre-beta bug batch), then this, then M7.13 (faces with holes, #121). All three ship before beta testers are invited.

## 1. Goal

A beta tester who hits a crash, a power cut or a forced close loses at most a few minutes of modelling, not their session. When they start Bermake again, it offers their unsaved work back. Their own `.berm` file is never overwritten unless they choose to save over it.

Success test: draw something, wait for an autosave, end Bermake from Task Manager, start it again, and get the work back, minus at most one autosave interval.

## 2. Decisions (maintainer, 2026-10-04)

- **D1. Location.** Autosaves live in Bermake's own folder, `%LOCALAPPDATA%\Parrow Horrizon Studio\Bermake\recovery`, beside `logs`. Never next to the user's drawing.
- **D2. Interval.** Every 5 minutes by default, changeable to Off, 1, 5, 10 or 30 minutes.
- **D3. Where the interval is set.** A **File > Autosave** submenu with those five checkable choices, like the Units menu. Bermake has no Preferences window, and this release does not add one.
- **D4. Recovery asks first and opens the work as unsaved.** The recovered document is not tied to the original file; saving it goes through Save As, pre-filled with the original folder and name.
- **D5. Approach C: wait for a pause.** An autosave becomes due at the interval and runs at the next pause in the user's work, or is forced one minute later.
- **D6. Out of scope.** Keeping older autosave versions, a backup copy of the `.berm` on every Save, and recovering several documents at once.

## 3. Why wait for a pause (measured)

Saving runs on the main thread: converting the model to plain data cannot leave it, because the model is not thread-safe. Measured on the development machine with `save_document`, on flat grids of square faces with no textures:

| Faces | Full save | Model to data | Compress and write |
|---|---|---|---|
| 2,500 | 30 ms | 22 ms | 10 ms |
| 10,000 | 113 ms | 82 ms | 28 ms |
| 40,000 | 456 ms | 331 ms | 83 ms |

Typical tester models (a few thousand faces) save in well under 100 ms, which nobody notices. A large imported model would hitch for about half a second. A plain timer would put that hitch wherever it fires, possibly in the middle of a drag. Moving compression and disk writes to a thread removes only about a quarter of it. Waiting for a pause puts the whole save where the user is not interacting, so it reuses the existing save code unchanged.

## 4. Design

### 4.1 Components

A new package, `python/bermake/recovery/`, holds the parts that do not need a window, so each can be tested without one:

- `store.py`: `RecoveryStore`. It writes, lists, deletes and quarantines recovery sessions in one folder, and knows nothing about Qt widgets.
- `scheduler.py`: `AutosaveScheduler`. It decides when an autosave should run. It is pure: the clock, the "is the user idle" query and the "may the model be read" query are injected.
- `liveness.py`: `process_is_running(pid, started_at)`. It tells whether the Bermake that wrote a session is still running.
- `startup.py`: `recoverable_sessions(store)`. It returns the sessions left by Bermakes that are no longer running, newest first.

The UI side:

- `python/bermake/ui/recovery_dialog.py`: the startup dialog.
- `MainWindow` wiring: the session ID, a `QTimer` that ticks the scheduler, an application-wide input filter, the File > Autosave submenu and File > Revert to Saved.
- `app.py` `_build_main_window`: runs recovery before the Welcome dialog.

### 4.2 What is written, and where

- The folder is `<AppLocalDataLocation>/recovery`, resolved the same way as `default_log_directory()` in `diagnostics/logs.py`, and created on first write.
- Each open document has a **session ID**, a random UUID4 hex string. A new one is made at window creation and on New, Open, Revert to Saved and Recover.
- Each session has two files:
  - `<id>.berm`, written by the existing `save_document()` with `thumbnail=None`. The thumbnail needs a live GL grab and is not needed for recovery. `save_document` is already atomic (temp file plus `os.replace`), so a crash during an autosave leaves the previous autosave intact.
  - `<id>.json`, the metadata, also written atomically (temp file plus `os.replace`), and always after the `.berm` succeeds:

    ```json
    {
      "format": "bermake-recovery",
      "version": 1,
      "session_id": "<id>",
      "original_path": "C:\\Users\\...\\House.berm",
      "display_name": "House.berm",
      "saved_at": "2026-10-04T14:32:05+08:00",
      "app_version": "0.17.0",
      "pid": 12345,
      "process_started_at": "2026-10-04T13:58:41+08:00"
    }
    ```

    `original_path` is `null` for a document that was never saved. `display_name` is then "Untitled".
- `RecoveryStore.list_sessions()` treats a `.json` without its `.berm` as damaged and a `.berm` without its `.json` as an orphan. Both are quarantined (4.5), never offered.

### 4.3 When the files are deleted

Files left in the folder must mean "this session ended abnormally". The current session's two files are deleted when:

- a Save or Save As succeeds; the saved file is now the newest copy
- the window closes normally; `closeEvent` accepted, after the existing unsaved-changes prompt
- New, Open or Revert to Saved replaces the document, after the existing discard prompt
A failed Save deletes nothing. Recover deletes nothing either: it hands the loaded session's files over to the new session (4.5), so recovered work stays protected even if Bermake crashes again before its next autosave.

### 4.4 When it saves

- **Interval:** File > Autosave offers Off, Every minute, Every 5 minutes (default), Every 10 minutes and Every 30 minutes. The choice is stored as the preference `autosave/interval_minutes` (`0` means Off) through new `read_autosave_interval` and `write_autosave_interval` functions in `ui/preferences.py`. Unknown values read as 5. Changing it restarts the countdown.
- **Changed since the last autosave:** the scheduler keeps its own `changed_since_autosave` flag, set by the same `_on_document_changed` hook that marks the document dirty, and cleared by a successful autosave or Save. An unchanged document is never rewritten, even if it is dirty.
- **Due, then idle:** a 1-second `QTimer` ticks the scheduler. When the interval has elapsed and there are changes, the autosave is *due*. A due autosave runs on the first tick where all of these hold:
  - no keyboard, mouse or wheel input for 2 seconds (an application-wide event filter records the time of the last input event)
  - no mouse button is held (`QApplication.mouseButtons()`)
  - the active tool holds no uncommitted changes to the model (below)
  - no modal dialog is open (a save prompt or file dialog)
- **Forced:** if it has been due for 60 seconds without a pause, the idle requirement is dropped. It still waits for the other three, so a forced save never captures a half-finished drag.
- **Uncommitted changes:** a new `Tool.holds_uncommitted_changes` property defaults to `False`. Committed edits are already in the model and are safe to save. A Line chain is a deliberate exception to the tool-by-tool rule: its finished segments are pushed only on Enter, yet Line reports no uncommitted changes mid-chain by ruling, because those segments are real visible edges and blocking autosave for a whole chain risks more work than it protects. An autosave mid-chain followed by Escape can leave the cancelled segments in the recovery file until the next edit. Only a tool that changes the model live during a gesture and rolls back on cancel must return `True` while it does. The implementation plan audits every tool for this, and a test pins the result per tool.
- **Failure:** an `OSError` (or `BermakeIOError`) during an autosave is logged as a warning with the traceback, shows a status-bar message ("Autosave failed; will retry"), keeps `changed_since_autosave` set, and is retried at the next interval. It never opens a dialog, and never raises into the event loop.
- **Status bar:** a successful autosave shows "Autosaved HH:MM" (local time, 24-hour) and keeps showing it, with no timeout. The next document change, a successful Save or Save As, and New, Open, Revert to Saved or Recover clear it, and any other status message that replaces it in the meantime is not overridden.

### 4.5 Recovery at startup

- **Where it runs:** `_build_main_window` in `app.py` runs recovery after `window.show()` and before the Welcome dialog. It never runs for `--smoke-test` (which returns before any window) or in a process that relaunched itself from the OpenGL preflight (which returns before building a window).
- **What counts as recoverable:** `recoverable_sessions(store)` lists valid sessions whose writer is not running. `process_is_running(pid, started_at)` returns `True` only if a process with that PID exists and its creation time matches `process_started_at` to within 2 seconds, so a reused PID is not mistaken for the original Bermake. On Windows this uses `OpenProcess`, `GetExitCodeProcess` and `GetProcessTimes` through `ctypes`, with no new dependency. Elsewhere it uses `os.kill(pid, 0)` plus `/proc/<pid>/stat` where available. If liveness cannot be determined, the session is treated as running and left alone.
- **The dialog**, `RecoveryDialog`, is modal over the main window:
  - **One session:** "Bermake closed unexpectedly. Recover *House.berm*, last autosaved today at 14:32?" with **Recover**, **Discard** and **Decide later**.
  - **Several sessions:** the same dialog with a list, newest first, and the first one selected. **Recover** recovers the selected one and keeps the rest for next launch. **Discard** discards the selected one. **Decide later** keeps all of them.
- **Recover:**
  - loads the session's `.berm` with `load_document`
  - replaces the window's document through the existing `_reset_document` path, with no file path
  - marks the document dirty
  - sets the title to "*House.berm (recovered)*"
  - starts a new session and hands the loaded session's files over to it: the `.berm` is renamed to the new ID, and the metadata is rewritten with the new ID and this process's PID and start time. The work is on disk under a live session from the first moment, and `changed_since_autosave` starts clear, because the disk copy already matches the window.
  - skips the Welcome dialog
  - The window remembers the session's `original_path` as the suggested save location. The next Save opens Save As (there is no path) with the original folder and file name pre-filled; `_prompt_save_path` gains an optional suggested path. An Untitled session suggests nothing.
- **Discard:** asks first: "Delete the autosaved work for *House.berm*? This cannot be undone." with **Delete** and **Cancel**, Cancel the default and Escape cancelling. **Delete** deletes the session's files and the Welcome dialog follows as usual. **Cancel** returns to the recovery dialog with every session still kept.
- **Decide later:** changes nothing. The Welcome dialog follows as usual.
- **A session that fails to load** (`BermakeIOError`, `OSError`, or a damaged or orphaned pair found by `list_sessions`) is quarantined: its files are renamed to `<id>.broken.berm` and `<id>.broken.json`, and kept. Quarantined files are never offered again and never deleted automatically. If the failure came from Recover, a message says the autosave could not be opened and names the folder where the file was kept. The quarantine and the reason are logged.

### 4.6 File > Revert to Saved

- A new action, **Revert to Saved**, sits in the File menu after Save As. It is enabled only when the document has a path and unsaved changes, and its enabled state updates whenever either changes.
- On trigger it asks: "Discard all changes since you last saved *House.berm*? This cannot be undone." with **Revert** and **Cancel**.
- On Revert it reloads the path through the same code as Open (`load_document` plus `_reset_document`), which also clears the undo history as Open does, then starts a new session and deletes the old session's files.
- If the file can no longer be read, it shows the existing "Open failed" message and leaves the current document untouched.

### 4.7 Tester-facing text

- `packaging/README.txt` gains a short "Autosave" paragraph covering:
  - the default interval and where to change it (File > Autosave)
  - that the recovery prompt appears after a crash
  - where the recovery folder is
  - that a `*.broken.berm` file there is worth attaching to a bug report
- The release notes describe the same.

## 5. Error handling summary

| Situation | Behaviour |
|---|---|
| Autosave write fails | Warning logged, status-bar message, retried at the next interval, no dialog |
| Recovery folder cannot be created | Same as a failed write; Bermake runs normally without autosave |
| Recovery file damaged or orphaned at startup | Quarantined as `.broken`, logged, never offered |
| Recover fails to load | Quarantined, message naming the folder, Welcome dialog follows |
| Liveness unknown | Treated as running; left alone |
| Two Bermakes at once | Separate sessions; neither offers the other's live work |
| Crash during an autosave | Previous autosave intact (atomic replace) |

Nothing in this feature may stop Bermake from starting: every recovery step at startup catches `Exception`, logs it, and falls through to the Welcome dialog.

## 6. Testing

- **`RecoveryStore`**, in temporary folders:
  - a write produces both files with the right metadata, and the metadata is written last
  - list, delete and quarantine
  - damaged and orphaned pairs
  - an atomic write survives a simulated failure mid-write
- **`AutosaveScheduler`**, with a fake clock and injected idle and safety queries:
  - nothing runs while unchanged, while Off, or before the interval
  - a due save waits for idle and runs on the first idle tick
  - a forced save runs at 60 s overdue but never while a button is held, a tool holds uncommitted changes, or a modal is open
  - a failure keeps the changes flag and retries next interval
  - changing the interval restarts the countdown
- **`process_is_running`:**
  - the current process is running
  - a PID that does not exist is not
  - the current PID with a wrong start time is not (PID reuse)
- **`recoverable_sessions`:** none, one, several (newest first), live writer skipped, damaged skipped.
- **MainWindow and app**, with offscreen Qt, temporary folders and patched prompts:
  - deletion on each trigger in 4.3, including the failed-Save case
  - the File > Autosave choices round-trip the preference
  - Revert to Saved: enabled state, confirm and cancel, reload, the unreadable-file case
  - Recover sets no path, the "(recovered)" title, dirty state, the suggested Save As path, and skips the Welcome dialog
  - Recover hands the files to the new session: after Recover, a simulated crash still leaves a recoverable session holding the recovered model
  - Discard and Decide later
  - recovery is skipped for `--smoke-test`
- **`Tool.holds_uncommitted_changes`:** a test lists every registered tool and its value during and after a representative gesture, so a new tool cannot silently skip the audit.
- **End-to-end crash test**, in a subprocess:
  - start a Bermake process with a short interval and temporary data folders
  - make a change and wait until the session files exist
  - kill the process hard (no clean exit)
  - start a second process and assert it finds exactly that session and can recover its model
- **Manual gate on the packaged zip:**
  - draw, wait for "Autosaved", end Bermake from Task Manager, restart, Recover, and check the geometry and the "(recovered)" title
  - Save opens Save As at the original location
  - Revert to Saved on a saved file

All new assertions are mutation-checked, as in previous milestones.
