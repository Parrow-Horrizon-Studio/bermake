# M7.8: Rename Pluton to Bermake

**Status:** approved, not yet implemented
**Ships as:** v0.14.0
**Sequence change:** the Windows build, previously M7.8, becomes M7.9

## 1. Context

Microsoft holds a trademark on "Microsoft Pluton", a silicon security processor
shipping in Windows PCs. A 3D modeller and a security chip are different classes
of goods, so a conflict is not certain, but "Pluton" plus software is close
enough to be a genuine nuisance for a product whose entire current phase is
about becoming visible to outside testers. The name is also a poor asset
regardless of the legal question: it is unsearchable, because searching for it
returns Microsoft's product.

The name becomes "Bermake", pronounced Ber-Make, with "make" as the English
word. It is coined, which makes it both searchable and defensible, the two
properties Pluton lacked.

### 1.1 Why now rather than later

This is the cheapest moment the rename will ever have, and the cost curve is
steep. Nothing is published under the old name that a rename would have to
migrate:

| Surface | State today |
|---|---|
| PyPI package | never published |
| Installer, signed binary, OS file association | none, those are M7.9 and M9 |
| `.pluton` files held by testers | none, no tester has started |
| Old GitHub URLs | a repository rename redirects them automatically |

Every row stops being free at M7.9 and M9. Once a tester holds a document, an
installed binary and a registered file association, the rename acquires a file
migration path, a settings migration and an installer upgrade story. Before the
Windows build this is about a day of work. After installers it is a milestone
plus breakage testers feel. That asymmetry, rather than the legal risk, is what
sets the timing.

### 2.2 Path renames

Only six paths carry the name. Everything else that matches does so because it
lives under the package directory, and one directory move handles all of it. All
moves use `git mv` so rename detection survives in history.

| Before | After |
|---|---|
| `python/pluton/` | `python/bermake/` |
| `cpp/include/pluton/` | `cpp/include/bermake/` |
| `python/pluton/io/pluton_file.py` | `python/bermake/io/bermake_file.py` |
| `tests/test_pluton_file.py` | `tests/test_bermake_file.py` |
| `docs/2026-05-16-pluton-design.md` | unchanged, see D4 |
| `docs/releases/v0.13.0.md` | unchanged, historical |

Measured scale for the content sweep: 8488 case-insensitive occurrences across
520 tracked files. Of those, 2155 are `import pluton` or `from pluton` lines
across 400 files, 5620 sit in 71 historical documents this milestone does not
touch, 233 are `pluton::` in C++, 24 are `namespace pluton`, and 23 are
`#include` lines naming the old include directory.

### 2.3 Build and tooling configuration

Listed individually because a miss here fails quietly rather than loudly, and
two of them are actively dangerous.

`pyproject.toml`:

- line 9, the distribution name.
- line 10, the version, see 2.7.
- line 43, `pluton = "pluton.app:main"`, the console script. Both halves change,
  and this is the command a tester types to launch the application.
- line 51, `wheel.packages = ["python/pluton"]`.
- lines 64, 66, 68 and 71, **per-file ruff ignores keyed on `python/pluton`
  paths**: `N802` for `viewport_widget.py`, `main_window.py` and
  `outliner_tree.py`, and `N818` for `tools/sweep_support.py`. If these paths
  are not moved in the same commit as the directory, the ignores match nothing,
  the suppressed violations resurface, and `ruff check` goes red on code nobody
  edited. This is the most likely way for this milestone to break CI, and it
  will present as an unrelated lint failure in files the rename barely touched.

`CMakeLists.txt`: the project name at line 14 and the version at line 15.

`cpp/CMakeLists.txt`: the `pluton_core` target at lines 2, 11, 17, 20 and 29,
the comment at line 24 naming the Python-facing module, and the install
destination at line 32.

`.github/workflows/build.yml`: the step label at line 70, and the lint gate
paths at lines 120 and 122. **A stale path here makes the gate pass while
checking nothing**, which is worse than failing.

`vcpkg.json`: the package name at line 2, and the homepage at line 5, which
becomes `https://bermake.org`.

`README.md`: 10 occurrences, including the launch command at line 128 and the
lint command at line 151.

`.git-blame-ignore-revs`: the rename commit is appended, following the M7.1
precedent already in that file. Without it, `git blame` on any of 400 files
leads to the rename rather than to the change that wrote the line.

### 2.4 The document format

The extension becomes `.berm`. Four characters puts it in line with every peer
format, `.skp`, `.3dm`, `.c4d`, `.fbx` and `.obj`, and no established format
claims it.

The manifest carries a format field and the loader validates it, so the rename
is a compatibility decision rather than a string replacement. The decision is a
hard break: the loader accepts `"bermake"` only.

The break must be loud and specific. A file written by Pluton must raise
`BermakeFormatError` with a message that says what the file is and why it cannot
be opened, naming Pluton explicitly. The one thing worse than a rejected file is
a rejected file whose message does not explain itself, so the generic
wrong-format message is not sufficient here.

`SCHEMA_VERSION` stays at 9. The payload schema did not change; the format's
identity did, and the format field already performs the rejection. Moving it to
10 would assert a payload change that does not exist.

The file dialog filters at `main_window.py` lines 2016 and 2200 become
`"Bermake files (*.berm)"`.

### 2.5 User-visible strings

59 string literals in production code carry the name. Those with behaviour
attached, rather than prose:

- `window_state.py` line 26, the Qt application name. This keys the QSettings
  store, so changing it orphans the stored theme, welcome-dialog and
  default-template preferences. Accepted rather than migrated, see D7.
- `document_controller.py` line 9, the constant that composes the window title.
- `main_window.py` line 138, the initial window title.
- `app.py` line 17, the startup console line, which the v0.13.0 release note
  tells testers to quote when reporting a bug.
- `gltf_codec.py` line 182 and `gltf_export.py` line 206, the generator field
  written into exported glTF. Changing it is correct and changes export output.
  No test asserts the literal value, verified by search, so nothing downstream
  needs updating.

### 2.6 Documentation

Historical documents are not rewritten. The 71 dated milestone specs and plans
in `docs/`, and `docs/releases/v0.13.0.md`, record what was true when they were
written. A document dated 2026-05-22 did not discuss Bermake, and editing it to
claim otherwise falsifies the record in the same way editing a shipped history
row would. This is also the decision that removes two thirds of the total work.

Living documents are updated: `README.md`, and the roadmap's content.

The roadmap gains a document-history row recording the rename, its reason and
its date, so a reader who meets "Pluton" in an older document can discover what
happened and when without having to ask.

### 2.7 Version

`0.13.0` becomes `0.14.0` in three places, all of which must agree:
`pyproject.toml` line 10, `CMakeLists.txt` line 15, and `cpp/src/version.cpp`
line 6. The third is C++, so this milestone requires a rebuild even setting the
namespace change aside.

A minor bump rather than a patch: the distribution name, import path, console
script, file extension and window title all change. That is not what a patch
release means.

### 2.8 Repository and local directory

The GitHub repository is renamed, which redirects old clone URLs and the 128
existing issue links automatically. The local `origin` remote is then updated
explicitly rather than left relying on the redirect.

The local working directory is renamed last, because it invalidates the working
directory of any running session, including the one performing the work.

## 3. Testing strategy

A rename has an unusually strong correctness oracle: **it must change no test
outcome at all.** The suite currently reports 2960 passed and 2 skipped under
the CI environment, and `ctest` reports 135. Any movement in those numbers is a
defect rather than a consequence.

Beyond that, four new tests:

1. **A guard test that greps for the retired name** across `python/bermake` and
   `cpp`, asserting zero occurrences. This is what catches the reference nobody
   thought of. It must be scoped to those two trees, because `docs` deliberately
   retains thousands of occurrences, and it must assert that its own scope
   matched a plausible number of files, so it cannot pass by searching nothing.
   A guard test that silently searches an empty tree is the exact failure this
   project hit twice in M7.7.
2. **The hard break, asserted rather than assumed**: a fixture carrying the old
   format field must raise `BermakeFormatError`, and the assertion must check
   that the message names Pluton, not merely that an exception was raised.
3. **A round trip** through `.berm`: save, reopen, compare.
4. **Import identity**: the package version and the native module version both
   report `0.14.0`, which also proves the rebuilt native module is the one being
   imported rather than a stale copy.

The three lint gates must pass with the ruff invocations pointed at the new
path, and the `ruff format --check` file count must still be 147, which is what
distinguishes a gate that inspected the tree from one that matched nothing.

## 4. Decisions

- **D1. The extension is `.berm`.** Four characters, in line with peer formats,
  no established claimant. `.ber` was rejected on evidence: it is the standard
  extension for ASN.1 Basic Encoding Rules data, listed across file-extension
  databases, in a domain whose users are precisely the developers most likely to
  have it already mapped. `.brm` is likewise taken. `.bermake` was rejected as
  out of step with every format in the industry and long in every file filter,
  test fixture and documentation example. The English word "berm", a raised bank
  of earth used in site grading, overlaps harmlessly: it is a word rather than a
  competing format, and it is faintly apt for an architectural modeller.
- **D2. Old documents break loudly.** The loader accepts the new format field
  only. Chosen over a dual-accept branch because no tester holds a document, so
  the only cost falls on local test models, and a permanent compatibility branch
  carrying a retired name is a durable tax for a transitional problem. The error
  message must name Pluton so the break explains itself.
- **D3. `SCHEMA_VERSION` stays 9.** Identity changed, schema did not.
- **D4. The roadmap keeps its filename.** It is referenced 90 times across
  roughly thirty historical documents. Renaming it either breaks those links or
  requires editing history that D6 says to leave alone. Its content is updated
  because it is living; its filename is a historical artefact of when the
  project began.
- **D5. Sequence and version.** The rename is M7.8 and ships v0.14.0; the
  Windows build becomes M7.9. The binary is then born under the new name and
  never needs redoing.
- **D6. Historical documents are untouched.** Rewriting them falsifies dated
  records. One rename row in the roadmap's history is how a reader connects the
  old name to the new one.
- **D7. Preferences reset rather than migrate.** Changing the Qt application
  name orphans the settings store. A migration shim would be permanent code
  serving a population of one machine. The reset is harmless: the theme returns
  to Light, the welcome dialog returns, and the default template returns to
  Architectural.
- **D8. Display name and identifier are the same word.** No split between a
  display name and a package name is needed, because `bermake` is already a
  clean identifier: lowercase ASCII, no digits, no collision.
- **D9. The rename commit is added to `.git-blame-ignore-revs`.** A mechanical
  sweep across 400 files otherwise destroys `git blame` for the whole package.
- **D10. Existing tags and releases keep the old name.** v0.13.0 and earlier are
  accurate historical markers. v0.14.0 is the first release under the new name.

- **D11. `tests/data/` is left untouched.** The glTF fixtures carry the old
  name as their own generator provenance, and two of them are binary `.glb`
  files that a text sweep cannot reach. Sweeping the JSON and the script while
  the binaries keep the old value would leave the fixture set internally
  inconsistent, which is worse than leaving it alone. Fixture provenance is
  data describing where a file came from, not product identity, and these
  files did come from Pluton.

## 5. Out of scope

- Any behaviour change. This milestone changes names, not conduct. A tempting
  cleanup noticed while sweeping 400 files belongs in its own commit or its own
  issue.
- A converter for existing `.pluton` files. If specific local models are worth
  keeping, converting them is a throwaway script run once before this lands,
  not a shipped feature.
- Reserving `bermake` on PyPI. Worth doing to avoid repeating this episode, but
  it is not a code change and does not gate the rename.
- Renaming the GitHub issues, commit messages and tags that mention Pluton.
  They are immutable records, and the repository redirect keeps their links
  working.
- A logo, icon or any other brand asset.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Stale ruff per-file-ignore paths turn the gate red on untouched code | Move them in the same commit as the directory; the lint gate runs before the suite, so this surfaces first |
| Stale lint paths in the workflow make the gate pass while checking nothing | Assert the checked file count is still 147 |
| The old distribution lingers in the editable install and shadows imports | Uninstall it explicitly before reinstalling, then assert the package resolves into the new tree |
| A missed reference survives in a rarely imported module | The scoped grep guard test, which asserts its own scope matched files |
| A C++ rebuild masks a namespace error as a link error | Rebuild before running either suite; `ctest` must report exactly 135 |
| A test asserting the glTF generator value fails and gets worked around | Does not arise: no test asserts the literal, verified by search. The change is safe |
| The local directory rename strands the session performing it | It is the final step, and the session is expected to restart afterwards |

## 7. Sequencing

No model conversion step is needed: there are no local `.pluton` models worth
keeping, so the hard break of D2 costs nothing at all.

1. C++ tree: move the include directory, sweep the namespace, include lines and
   prose, rename the library target. The install destination stays as it is,
   because the Python package directory has not moved yet.
2. Python package and its importers: move the directory, sweep `python/` and
   `tests/`, rename the error classes, and update the build configuration,
   which includes the ruff ignore paths, the console script, the wheel package
   path, the workflow lint paths, `vcpkg.json`, and the CMake install
   destination. Reinstall.
3. Format: extension, format field, the loud rejection message, dialog filters,
   and the two format module renames.
4. Version to 0.14.0 in all three places, then rebuild.
5. The grep guard test.
6. Documentation: README, roadmap content, roadmap history row, a release note
   for v0.14.0, and `.git-blame-ignore-revs`.
7. Full verification: rebuild, pytest, ctest, three lint gates.
8. GitHub repository rename, then update the `origin` remote.
9. Local directory rename, last.

## 8. Open items

None. Both items raised during review are resolved: the homepage becomes
`https://bermake.org`, and there are no local `.pluton` models worth keeping,
so no conversion step is needed.
