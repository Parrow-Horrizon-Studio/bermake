# M7.9: Windows Build

**Status:** approved, not yet implemented
**Ships as:** v0.15.0
**Closes:** #130, #135, #136

## 1. Context

Phase 2.6 exists so that outside testers who use SketchUp daily can run
Bermake and report back. Today they cannot: running Bermake means assembling
MSVC, vcpkg, CMake and Python, then building a native extension. M7.9 removes
that barrier with a build a tester can download, unzip and double-click.

It serves a second reader as well. The next milestone, M7.10, fixes the
tester-visible issues before anyone outside is invited, and those fixes should
be verified on the artefact testers will actually run, not only in a dev
checkout. A packaged application fails in ways an editable install cannot
show: a Qt plugin not collected, a data file left behind, a DLL resolved from
a developer's PATH that a clean machine does not have.

The roadmap fixes the boundary: not signed, not an installer, not
cross-platform. Those stay with M9.

### 1.1 What makes this tractable

Three properties of the current tree, verified before this design was written:

| Property | Consequence |
|---|---|
| Assimp and its transitive deps link statically into `_core` (`x64-windows-static-md`, root `CMakeLists.txt`) | No native DLLs beyond Python's and Qt's to collect |
| Icons (44 SVGs) and shaders (8 files) load through `importlib.resources`, never through paths built from `__file__` | Collecting them as package data is sufficient |
| The application imports five Qt modules: QtCore, QtGui, QtWidgets, QtOpenGLWidgets, QtSvg | The bundle can leave most of PySide6's ~640 MB installed footprint behind |

### 1.2 What a tester currently cannot survive

Three gaps would make a tester's first report uninformative:

- **A windowed executable has no console.** The startup `print` goes nowhere,
  and so does every uncaught exception. A crash looks like the window
  vanishing, with nothing to send.
- **The shaders require OpenGL 3.3 core and nothing checks for it.** No
  `QSurfaceFormat` is requested. A tester in a virtual machine, over Remote
  Desktop or on an old integrated GPU gets a broken viewport or a crash and no
  explanation.
- **There is no About dialog.** A tester cannot tell you which version they
  are running.

M7.9 closes all three alongside the build.

## 2. Scope

### 2.1 Delivery: a portable zip

The deliverable is `Bermake-<version>-windows-x64.zip`, containing a
`Bermake/` folder with `Bermake.exe`, its dependencies, and a tester
`README.txt`. Unzip anywhere and double-click. Deleting the folder uninstalls
it; stored preferences remain in the registry as they do for a dev run. There
is no Start Menu entry and no `.berm` file association.

### 2.2 The build pipeline

**Local command:** `.venv/Scripts/python tools/package_windows.py`. It runs
five stages, stopping at the first failure:

1. **Clean build venv.** Create `build/package-venv`, separate from the dev
   `.venv`, and install PyInstaller into it.
2. **Real wheel install.** `pip install .` (not `-e`) into the build venv,
   constrained by `packaging/constraints.txt`. This is the fix for #136: every
   build proves that `tool.scikit-build.wheel.packages` in `pyproject.toml`
   and `install(TARGETS _core LIBRARY DESTINATION bermake)` in
   `cpp/CMakeLists.txt` agree, which today only human inspection guarantees.
   If `CMAKE_TOOLCHAIN_FILE` is unset, the script supplies
   `C:/vcpkg/scripts/buildsystems/vcpkg.cmake` when that file exists and
   otherwise fails naming the variable, so the build does not rediscover #137.
3. **PyInstaller, onedir mode,** against the checked-in spec
   `packaging/bermake.spec`. The spec collects the icon and shader directories
   as package data, restricts Qt to the five modules plus the `windows`
   platform plugin, the SVG image format plugin and `opengl32sw.dll`, sets
   `console=False`, and embeds a Windows version resource generated from the
   built package's `__version__`.
4. **Smoke test** of the built executable (section 2.6).
5. **Zip and size check.** Copy `packaging/README.txt` into the folder, write
   `dist/Bermake-<version>-windows-x64.zip`, and fail if the zip exceeds
   **100 MB**.

The script is the only code that knows PyInstaller is the packager. Local and
CI builds run the same script, so they cannot drift apart.

**Pinned inputs.** `packaging/constraints.txt` pins exact versions of PySide6
(and its Essentials, Addons and shiboken6 wheels), numpy, PyOpenGL,
mapbox-earcut and PyInstaller. `pyproject.toml`'s runtime dependencies stay
unpinned floors, which is correct for the package; the constraints file
applies only to packaging, so a new upstream release cannot silently change
what testers receive. Upgrading is a deliberate edit to that file.

### 2.3 CI

A new job, `package-windows`, in `.github/workflows/build.yml`, on
`windows-2022`. It reuses the build job's vcpkg setup (`lukka/run-vcpkg` at the
same pinned commit, the binary cache, `CMAKE_TOOLCHAIN_FILE`) and runs
`tools/package_windows.py`.

- **Push to `main`:** upload the zip as a workflow artifact, retained 30 days.
  This is how a fix is tested on the packaged application without cutting a
  release.
- **Push of a `v*` tag:** first assert the tag equals `v` followed by the
  `pyproject.toml` version, failing before anything is published if not.
  Then create a **draft** GitHub release for the tag with the zip attached.
  Release notes and publishing stay human steps.

The workflow's top-level `permissions: contents: read` stays. Only the job
that creates the draft release is granted `contents: write`, and it runs only
on tag pushes.

### 2.4 Diagnostics

All of this lives in the application, so it works identically from the dev
checkout.

**Logging and crash capture**, in a new `python/bermake/diagnostics/` package:

- **Log file.** `bermake.log` in a `logs` folder under
  `QStandardPaths.AppLocalDataLocation`, which with the existing organisation
  and application names resolves to
  `%LOCALAPPDATA%\Parrow Horrizon Studio\Bermake`. A `RotatingFileHandler`,
  1 MB per file, 3 backups. Configured in `main()` before `QApplication` is
  constructed, which requires setting the organisation and application names
  through the static `QCoreApplication` setters first.
- **Session header.** The startup `print(f"Bermake {__version__}")` becomes a
  log line recording Bermake, Qt, PySide6 and Python versions.
- **Uncaught Python exceptions.** `sys.excepthook` and `threading.excepthook`
  write the full traceback to the log. PySide6 reports exceptions raised in
  Qt slots through `sys.excepthook`, so handler code is covered too.
- **Qt messages.** `qInstallMessageHandler` routes Qt's own warnings into the
  log. Shader compile errors, which today disappear, arrive this way.
- **Native crashes.** `faulthandler` is enabled against a separate,
  permanently open `native-crash.log`, so a crash in C++ or in the GPU driver
  that kills the process before Python can react still leaves a stack trace.
- **The dialog.** The first uncaught exception in a session shows a modal
  message: Bermake hit an error, details were saved to the log, with an
  **Open log folder** button. Later exceptions in the same session are logged
  without a dialog, because an exception inside `paintGL` would otherwise
  raise one per frame. The application continues running after the dialog,
  matching today's behaviour.

**OpenGL 3.3 check and software rendering:**

- **The check.** When the viewport first receives its context, a pure
  function takes the context's reported version and the per-shader compile
  results and returns a verdict. A context below 3.3, or any shader that
  failed to compile, produces a message naming the version obtained and the
  `GL_RENDERER` string, instead of a black viewport or a crash.
- **The fallback.** PySide6 ships `opengl32sw.dll`, Mesa's llvmpipe software
  rasteriser, which provides OpenGL 4.5 core on any machine. The message
  offers **Restart using software rendering**. Choosing it writes a
  preference and relaunches with the original command line: `sys.executable`
  plus `sys.argv[1:]` when frozen, and `sys.executable` plus
  `sys.orig_argv[1:]` from a dev checkout, where the executable is the Python
  interpreter rather than Bermake. Qt only honours
  `Qt.AA_UseSoftwareOpenGL` when set before `QApplication` exists, so
  `main()` reads the preference first. Software rendering is slower but makes
  virtual machines, Remote Desktop and old GPUs usable.
- **Turning it off.** A checkable **Help > Use Software Rendering** action
  toggles the preference and offers a restart. A `--software-opengl` command
  line flag forces it for one launch without touching the preference.

**About dialog.** **Help > About Bermake**, beside the existing Welcome
entry, in a new `python/bermake/ui/about_dialog.py`. It shows the Bermake
version; Qt, PySide6 and Python versions; `GL_VERSION` and `GL_RENDERER`;
whether software rendering is active; and the log folder path. A **Copy
details** button places all of it on the clipboard as plain text, ready to
paste into a GitHub issue.

### 2.5 One version source (#130)

Four hand-maintained version literals become one:

| Literal | Today | After M7.9 |
|---|---|---|
| `pyproject.toml` `version` | `0.14.0` | **the single source** |
| `CMakeLists.txt` `project(VERSION)` | hand-written | read from `pyproject.toml` at configure time with `file(STRINGS)` and a regex, so it works under scikit-build-core and under the standalone `build/tests` configure alike |
| `cpp/src/version.cpp` | returns a literal | returns a compile definition supplied from `PROJECT_VERSION` |
| `vcpkg.json` `version` | `0.0.1`, stale since M0 | field removed; vcpkg requires version fields only of manifests published as ports. The plan confirms this with a clean configure before relying on it |

`test_the_declared_and_the_compiled_version_agree` keeps asserting that
distribution metadata and `_core.version()` agree. That comparison is not
circular: metadata arrives through scikit-build-core reading
`pyproject.toml`, and the compiled string through CMake's regex and the
compiler. It drops its trailing `== "0.14.0"`, so a version bump is a
one-line edit. The existing `test_core_version_matches_semver_pattern`
already catches the regex producing an empty or malformed string.

The executable's version resource and the zip's filename derive from the
built package's `__version__`, and the CI tag check (section 2.3) compares
against `pyproject.toml`, so no fifth literal is introduced.

### 2.6 The packaged smoke test (#136)

`Bermake.exe --smoke-test <report.json>` runs inside the built executable,
since that is what ships. Implemented in
`python/bermake/diagnostics/smoke.py`, dispatched from `main()` before any
window is created. It writes a JSON report with one entry per check and exits
non-zero if any check fails.

1. **Imports.** `bermake` and `bermake._core` import, and
   `bermake.__version__` equals distribution metadata.
2. **Resources.** Every icon and shader loads through the same
   `importlib.resources` calls the application uses. The report records the
   counts. The build script counts the corresponding files in the source tree
   and fails on a mismatch, so a file left out fails the build without anyone
   maintaining a number by hand.
3. **Document round-trip.** Build a model, save it as `.berm` to a temporary
   directory, reopen it, and compare the geometry.
4. **Rendering.** With software rendering forced, create a hidden context,
   compile every shader, and render one frame of the scene renderer into an
   offscreen framebuffer. One check proves `opengl32sw.dll`, the shader files
   and frozen PyOpenGL all arrived. CI runners have no GPU, so software
   rendering is the only path available there regardless.

A pytest test runs checks 1 to 3 from the dev tree, so the smoke module cannot
rot between releases. Check 4 is exercised only by the package build, because
the offscreen platform pytest uses under `CI=true` cannot create a GL context
(`tests/conftest.py`). This is a stated gap, not a silently skipping test.

The flag ships in the product deliberately: asking a tester to run it and send
the report is a useful first diagnostic.

## 3. Testing strategy

**Automated, in pytest**, each with its collaborators injected:

- The OpenGL verdict function across versions below, at and above 3.3, and
  with a failed shader.
- Reading the software rendering preference, the `--software-opengl` flag,
  and that either one sets `AA_UseSoftwareOpenGL`.
- The relaunch, with process starting replaced by a recorder, so nothing
  actually restarts.
- The error dialog's once-per-session rule, with the dialog replaced by a
  recorder.
- The log directory resolution and handler configuration, against a
  temporary directory.
- **The native crash path, in a subprocess.** A child interpreter enables the
  crash capture against a temporary directory and calls
  `faulthandler._sigsegv()`; the test asserts `native-crash.log` exists and
  contains a stack trace. No other test can prove this path.
- The About dialog's copied text contains each field.
- Smoke checks 1 to 3.

**Every new assertion is mutation-checked:** the guarded code is broken and
the assertion is observed to fail. M7.7 and M7.8 each shipped tests that could
not fail, and every one was found by running, never by reading.

**Automated, in the package build:** all four smoke checks against the
frozen executable, the resource count comparison, and the size ceiling.

**Manual clean-machine gate, before tagging.** The smoke test cannot see
SmartScreen or real drivers, so this is a human gate.

1. **The developer machine.** Unzip outside the repo. Launch, run the welcome
   dialog, model, save, reopen, check About and Copy details, confirm the log
   exists.
2. **Windows Sandbox,** as a genuinely clean machine: no Python, no Visual
   C++ runtime, no developer PATH to mask a missing DLL. Sandbox very likely
   lacks hardware OpenGL 3.3, which makes it the real test of the check and
   the fallback: the message appears, the software restart works, modelling
   works. Enabling the Windows Sandbox feature is a system setting and is
   done by the developer, not by an agent.

## 4. Decisions

- **D1. PyInstaller, onedir.** Mature, maintained hooks for PySide6, numpy and
  PyOpenGL; builds in one to two minutes, which matters for a rebuild-to-test
  loop. Nuitka and `pyside6-deploy` were rejected for 10 to 30 minute builds
  and friction with the scikit-build extension; cx_Freeze for weaker PySide6
  support with no offsetting gain. Onefile was rejected because it unpacks to
  a temporary directory on every launch, which is slow and attracts
  antivirus heuristics.
- **D2. Portable zip, no installer.** Per the roadmap. Installers, signing and
  file association stay with M9 (#76).
- **D3. Build from a real wheel in a clean venv.** Closes #136 as a side
  effect of every build rather than as a separate CI job.
- **D4. Exact pins for packaging only.** The package keeps floors; the shipped
  artefact is reproducible.
- **D5. `pyproject.toml` is the version source.** CMake reads it; `vcpkg.json`
  loses its version; the version test loses its literal.
- **D6. Tags produce a draft release.** Publishing is outward-facing and stays
  a human action.
- **D7. Software rendering is offered, not automatic.** A silent fallback
  would hide a driver problem and hand the tester a slow application with no
  explanation. The tester chooses, and can reverse it from the Help menu.
- **D8. One error dialog per session; the application continues.** Prevents a
  per-frame dialog loop and preserves today's behaviour.
- **D9. Logs stay local.** Nothing is uploaded; the tester decides what to
  send.
- **D10. The smoke mode ships in the product.** It costs nothing at runtime
  and doubles as a support tool.
- **D11. The rendering smoke check runs only in the package build.** Stated as
  a gap rather than hidden behind a skip.
- **D12. 100 MB zipped ceiling,** against an estimated 50 to 70 MB.
- **D13. Ships as v0.15.0,** the first release with a downloadable asset.
- **D14. #135 is folded in,** since the README is edited for the download
  section regardless.

## 5. Out of scope

Code signing; an installer; `.berm` file association (#76); auto-update;
Linux and macOS builds; uploading crash reports or logs anywhere; telemetry;
the two tautological version tests (#129); fixing the in-repo venv's
non-relocatability (#137), which the build script sidesteps without fixing.

## 6. Risks

| Risk | Mitigation |
|---|---|
| Antivirus false positives on an unsigned PyInstaller build | Onedir mode; the tester README explains it; signing in M9 is the fix |
| PyInstaller hooks lagging Python 3.13 or PySide6 6.11 | Exact pins; the smoke test fails loudly rather than shipping a broken zip |
| A GitHub Windows runner cannot create a software OpenGL context | Measured at the first CI run (section 7). If it cannot, check 4 runs in the local build only, and section 2.6 records the gap |
| Hooks pulling in PySide6 Addons or unused Qt modules | Explicit module list in the spec; the 100 MB ceiling fails the build |
| The error dialog itself raising | The dialog path catches its own failure and falls back to logging only |

## 7. Sequencing

Each task leaves the tree green.

1. **One version source** (#130).
2. **Logging and crash capture.**
3. **OpenGL check and software rendering,** including the preference, the
   flag, the relaunch and the Help menu action.
4. **About dialog.**
5. **Smoke mode.**
6. **Packaging:** constraints, spec, build script, tester README, size check.
   Green when the local build produces a zip whose smoke report passes all
   four checks.
7. **CI package job:** artifact on `main`, tag check and draft release on
   tags. Its first run on a push is also the measurement of the software GL
   risk.
8. **Documentation:** `README.md` (#135 and the download section), release
   note, roadmap.
9. **Manual clean-machine gate,** then tag `v0.15.0` and publish the draft.
